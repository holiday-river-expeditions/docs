## Find Your Trip wizard, first build (feature/trip-finder, uncommitted to main)

The Aug 20 "sample question wizard" request, built end-to-end behind a new `trip-finder` demo flag (default OFF). Research pass first: vault sweep, live-site + arta.org UX research (holidayriver.com 301s to bikeraft.com — same site; neither Holiday nor ARTA has an actual wizard, only ARTA's three dropdowns plus editorial scaffolding), and NN/g/guided-selling literature. Question set drafted from ARTA's own choose-a-trip hierarchy (who/age → month → days → thrill → activity), all skippable, need-based wording ("How much whitewater do you want?" not "Select rapids class"). `TRIP_FINDER_QUESTIONS` in `src/lib/trip-finder.ts` is the single file Lauren's real questions replace.

Architecture: no client state machine at all — the wizard is fully server-rendered and the entire state is the URL query string (`/trip-finder?who=kids&age=8-12&…`), the OpenSeatsFilterBar pattern scaled up. Every answer option is a plain link adding one param; the server derives the current step as "first unanswered question"; Back drops the last param; results-screen answer chips drop one param each and land back on exactly that question. Shareable, back-button-native, works without JS. Only client component is the floating pill (usePathname to hide itself on /trip-finder; bottom-left since bottom-center and bottom-right are taken).

Matching is a pure weighted scorer (`scoreTrips`): weights follow ARTA's hierarchy (thrill 3, age 3, days/month/activity 2), unknown trip data scores a neutral 0.5 (critical — only 6 of ~25 trips carry wizard fields), skipped questions drop out of the average entirely, and a failed minimum age demotes below every clean fit with a month-aware caveat ("Minimum age is 16 in June — try July, when kids 8+ can come"). Results = 1 best match with why-it-fits reasons + 2 alternates + live Arctic availability (month-filtered `filterByMonth`/`nextAvailable`, deep link `/book?month=YYYY-MM#trip-sanity-slug` via `groupAnchor`, now exported from lib/departures). Arctic down degrades to the phone line.

Schema: four new trip fields — `maxRapidClass` (1–5 radio; deliberately NOT built on the contested easy/moderate enum — this is the working example for the parked difficulty-vs-class decision), `seasonMonths`, `minAgeOverrides` (months/age/reason, models Cataract's 8-but-16-in-May/June), `craftTypes` (powers ARTA's "thrill dial within a trip" — craft variety earns a scoring bonus so one trip serves a mixed-appetite family). Seeded via `scripts/seed-trip-finder-fields.mjs` (patch-by-slug, not createOrReplace) with PLACEHOLDER values needing Holiday's confirmation, esp. Westwater/Lodore/Yampa min ages and Yampa's season window. Dedicated `tripFinderTripsQuery` so /book's query stays lean.

Entry points (all flag-gated by CSS, markup ships hidden): homepage "Find Your Trip" section below the trip grid with question 1 inline (first click is already an answer), plus the floating site-wide pill. `/trip-finder` added to RESERVED_SLUGS and both wizard + results URLs to the axe e2e suite. 118 unit tests + 23 e2e green; verified live in the browser (family/July/splash correctly picks Desolation over Lodore on trip length).

Incidental fixes: demo-flags panel now scrolls (`max-h-[85vh]`) — the ninth flag row pushed controls off 720px viewports, breaking clicks; Playwright port is now env-overridable (`PORT=…`) because `reuseExistingServer` + a second session's dev server on 3000 silently tests the wrong code. Verified against the published dataset: `river-westwater.description` is populated (updated 06:14 today) and renders correctly at `/rivers/westwater`; `trip-westwater-canyon.description` is `null`. Content published successfully, into the neighbouring document.

**Root cause is the model, not the plumbing.** Findings, verified with GROQ against `production` and against `main` at `ef3b95a`:

- `tripCategory` and `activity` partition all six trips identically — Whitewater Rafting/River Rafting and Mountain Biking/Mountain Biking. Both load-bearing: `categories[0]->name` supplies the trip-card tag (colour chosen by `/bik/i.test(category)` in `TripCard.tsx:40`, a regex, not a field), `activities` drives `/rafting`, `/biking`, the trip-finder scorer (`lib/trip-finder.ts:641`) and the related-trips fallback. Two types, one distinction.
- Five document types each carry a field titled exactly "Description" with no help text. `trip.description` is empty on **all six** trips, so the fallback at `trips/[slug]/page.tsx:177` — "Trip description coming soon. Add it in the Studio." — is live on all six production trip pages.
- Studio structure pins only the two singletons and falls through to `documentTypeListItems()`: a flat alphabetical list with the contact/newsletter inboxes filed among the content types. `trip.ts` has 44 `defineField` calls and zero `groups`/`fieldsets`.
- `river` holds 9 docs named by canyon section; Maze and White Rim have `riverName: null` (not rivers); San Juan, San Rafael, White Rim have zero trips.
- Duplicate encodings on `trip`: `difficulty`/`maxRapidClass`, `duration`/`durationLabel`, `season`/`seasonMonths` (4 of 6 trips have months but no season string), and `specialtyTypes[]` vs `specialtyDepartures[].specialtyType`.
- Coverage: 1 of 5 specialty families has a trip (empty ones degrade gracefully to a "dates being finalized" note, verified on the live `/specialty`); 6 trips authored of ~25 bookable.

Measured Justin's "Trip Pages Suggested Build Out" against the Trip schema: 10 of its content requirements have no field — meeting place, deposit, who's-this-trip-for, what's included, packing list, getting here, before you go, video, combo tag, and the trip-page map (still hardcoded in `lib/trip-map-data.ts`).

Second pass over the schemas surfaced more, folded into the artifact:

- Studio sidebar order is **schema-registration order**, not alphabetical (`index.ts:16-39`): River, Activity, Trip Category, Specialty Type, Trip, FAQ, Page, Blog Post, Contact Submission, Newsletter Subscriber. The four taxonomies land first as consecutive unlabelled siblings.
- `riverName` was only half-applied: card projections use `coalesce(riverName, name)` (8 sites) but `riverBySlugQuery` (`queries.ts:121-128`) projects bare `name` — a card reading "Colorado River" links to a page headed "Westwater". Live inconsistency.
- `specialty-type.ts:11` still tells editors the type "renders its own parent page at `/specialty/[slug]`". That route was removed in the August restructure.
- Dead surfaces: `trip.pricingNotes` is projected twice (`queries.ts:9`, `:70`) and rendered nowhere; `getAllRivers()` and `getAllActivities()` have zero callers; `homepage.rivers[].tripCount`/`tripSlug` are per-river subqueries orphaned when the carousel retired in `4230abc`.
- `/rafting` and `/biking` hardcode their activity slugs, so a third Activity document is authorable but unreachable — directly relevant if Combo becomes a taxonomy member.
- `startingPrice` is a hand-typed string on every card while Arctic holds the authoritative price; both field descriptions already say pricing comes from Arctic.
- `coalesce(ribbon, specialtyTypes[0]->ribbonLabel)` is copy-pasted at 7 sites plus a divergent 8th (`queries.ts:194`, scoped `^.ribbonLabel`) which can disagree when a trip belongs to more than one specialty family.
- `craftTypes` is a third thrill signal alongside `difficulty` and `maxRapidClass` (`trip-finder.ts:543-547`).
- Singletons are pinned by id but have no action filtering — a stray second `homepage` doc would be invisible in the sidebar yet still reachable via `*[_type=="homepage"][0]`.
- `trip.faqs[]` draws from the same `faq` collection as `/faq`, with no flag distinguishing trip-scoped from global, so a trip answer also appears site-wide. The `faq.category` enum is duplicated as a hardcoded array in `faq/page.tsx:16-22`.
- `lib/trip-map-data.ts` joins hardcoded coordinates to rivers **by slug** and silently drops unmatched ones — so the River→Section rename must keep slugs untouched.

Artifact validated before publish: balanced tags, every custom property defined in the bare `:root` light baseline, both dark blocks covering the identical 17 tokens, no literal colours in component CSS.
